Kernel TLS on bare metal, Linux 7.0: runs on 2026-11-13 (21:00 to 23:00 UTC)

Machine: br-2 (AMD EPYC 4345P, 8 cores / 16 threads, 64 GB), the same hardware as
../machine.txt; kernel 7.0.0-43-generic, `tls` module loaded (`modprobe tls`), which
reported: "kTLS available: TLS 1.2 AES-128-GCM AES-256-GCM ChaCha20-Poly1305, TLS 1.3
AES-128-GCM AES-256-GCM ChaCha20-Poly1305, key updates yes". Loopback only.
Before each run: `GIONG_KTLS_REQUIRED=1 cargo test --release -p giong-tls --test ktls`
passed (19 tests, none skipped).

Method: bench/tls.sh (server on one core, wrk -t3 -c50 on three others, 5 rounds of
5 s, medians), TLS 1.3 with AES-256-GCM and an ECDSA P-256 certificate.
giong-http-tls = rustls in the process (Ktls::Off); giong-http-ktls = the same server
with Ktls::Required. `bytes*` answer from memory, `file*` from a 16 MiB file each worker
keeps open (`Body::file_range`): sendfile over plain TCP and kernel TLS, pread + rustls
in the process. `file64k-open` opens the file for every request. us/req is the server's
CPU time (user + system) per request.

5. Where the time goes, file1m (bench request 4c, perf record -g -p <server>, 10 s)

kernel TLS + sendfile (6,049 req/s): aes_gcm_enc_update_vaes_avx512 24.6%,
kernel_init_pages 10.7%, then nothing above 1.6% (read_tsc, nftables, pipe buffer
release, skb handling, tcp_sendmsg_locked).
rustls in the process (4,492 req/s): ring's aes_gcm_enc_update_vaes_avx2 36.9%, memcpy
9.4% + 1.5%, kernel_init_pages 7.4%, _copy_to_iter 6.1% (pread), _copy_from_iter 4.8%
(send).

Reading: with sendfile the ~20% spent copying disappears and the kernel's AVX-512
AES-GCM does the encryption. Page zeroing on allocation (init_on_alloc=1, Ubuntu's
default) is the next cost; booting with init_on_alloc=0 should give the kernel TLS path
roughly another 10%. ufw's nftables rules cost 2-3% in every mode, even on loopback.
