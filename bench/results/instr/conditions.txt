2. CPU-dependent code paths. glibc picks memcpy/strlen variants and ring picks
   AES-GCM code by CPU feature, so runners with other CPUs could count otherwise.
   Forcing glibc onto very different paths (GLIBC_TUNABLES), io_uring:

   case             default    hwcaps=-AVX2,-ERMS,-FSRM    x86_rep_movsb_threshold=100000
   http1            11143      11131 (-0.11%)              11140 (-0.03%)
   h2               54722      54594 (-0.23%)              54742 (+0.04%)
   https            46794      46736 (-0.12%)              46792 (-0.00%)
   postgres-query   12705      12718 (+0.10%)              12705 (0)

   Real runners differ far less than this (all have AVX2, ERMS, AES-NI). Hence a
   limit of 1%, ten times the spread of item 1 and four times the worst shift here.

3. Negative control: a loop planted in giong-http's `Response::write_head` (not
   committed). 40 iterations: http1 +0.39% (io_uring), +0.44% (epoll), web +0.31%,
   seen but within the limit. 150 iterations: http1 +5.42% / +6.06%, web +4.00% /
   +4.34%, and `scripts/instr.py check` failed with exit status 1, naming the four.
   tcp-echo and h2 (which do not use that function) did not move.

4. Heap per idle HTTP/2 connection, 5,000 connections, five runs on io_uring when
   the connections were opened as fast as possible: 4354.8 4314.5 4320.1 4621.7
   4313.0 bytes (7% apart): with thousands of prefaces queued at once the receive
   buffer pool runs low and the driver moves data to the heap, by timing. Opening
   them one at a time (waiting for each server SETTINGS): 4298.8 in all five runs,
   which is what bench/instr does.

5. Heap state (2026-11-20). glibc's malloc does different work for the same
   allocations depending on what the heap looks like: whether a freed chunk merges
   with its neighbour, whether a bin is searched or consolidated. The same binary
   of main 0387cfd, copied to a one-letter name, counted 12,620 instructions per
   postgres-query on epoll instead of 12,304 (+2.6%), all of it in `_int_malloc`
   (+150), `unlink_chunk` (+81), `_int_free_merge_chunk` (+69), `malloc_consolidate`
   (+56), `_int_free` (-54): the program's path is copied to the heap at start and
   its length decides where later chunks land. Unrelated changes move the heap the
   same way, and CI showed the same two states: #158 and #162 failed with epoll
   12,634 and 12,632 against a baseline of 12,345, #142 moved io_uring from 13,175 to
   12,855, on Intel and AMD runners alike, to the decimal.

   Since then a `run` is served by an allocator of the benchmark's own
   (bench/instr/src/alloc.rs: power-of-two size classes, a free list per class),
   whose cost depends only on the sizes asked for. Five heap states, before and
   after, every case: heap-state.txt. The spread of postgres-query went from 2.54%
   to 0.00%, mysql-query on epoll from 2.00% to 0.00%, h2 from 0.46% to 0.02%.

   The pull requests that tripped, rebuilt with the new allocator on the main they
   were tested with (c963367), postgres-query on io_uring / epoll:
     main c963367          11463.3 / 10998.7
     #158 (giong-postgres) 11476.3 / 11011.7   +0.11% / +0.12%
     #162 (giong-tls)      11456.3 / 10991.7   -0.06% / -0.06%
     main 0387cfd (#142)   11497.4 / 11032.7   +0.30% / +0.31%
   With glibc's malloc the same four measured 13174.3 / 12303.7, 13177.3 / 12306.7,
   13186.3 / 12315.7 and 12855.3 / 12340.7 here; CI, where the binary has another

   Negative control (not committed): a loop planted in giong-postgres's
   `parse_backend`. 2 iterations: +0.10% / +0.11%. 20 iterations: +0.73% / +0.76%,
   seen and within the limit. 60 iterations: +2.12% / +2.21%, and

6. Heap per idle connection across CI runners (2026-11-17 to 2026-11-20, the `instr`
   artifacts of 17 runs of the same code on GitHub's runners: Xeon 6975P-C on
   7.0.0-1014-aws, EPYC 7763, EPYC 9V45, EPYC 9V74 and Xeon 8573C on 7.0.0-1017-azure;
   three rounds each, bytes per connection, lowest and highest of all rounds):

   case         io_uring               epoll
   idle-http1    1964.2 to  1964.9      2142.4 (one round of all: 2162.9)
   idle-h2       4427.0                 4508.0
   idle-https   10764.7 to 10766.8     10816.3 to 10818.4

   So the heap agrees within 0.04% whatever the runner's CPU and cloud, and the one
   stray round (+0.96%) is absorbed by the median of three. Before #142 the three epoll
   rows were 16 bytes lower on every runner (2126.1, 4491.6, 10800 to 10802): a real
   change, seen identically everywhere. The resident set of idle-h2 moves by up to 2.7%
   between rounds of one run (4698 to 4827 on io_uring).

   The baseline's idle rows had been measured on a development VM, where idle-http1
   is 1940 on one kernel build and 1965 on another, and the limit was 2%: #162 added
   216 bytes to an idle HTTPS connection (10,765 to 10,981, +2.0% against CI's own
   number) and passed at +1.8% against a baseline of 10,783.8. Since then the idle rows
   come from a CI run and the heap limit is 1%, which that step would have failed.
