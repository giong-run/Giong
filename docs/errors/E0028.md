# GIONG-E0028: the system ran out of network buffers

Raised by `TcpStream` and `UnixStream` writes and connects, and by `UdpSocket` sends, on macOS. In code: `giong::error::Code::NetworkBuffersExhausted`. The error kind is `OutOfMemory`, and the kernel's `ENOBUFS` is the `source()`, so `raw_os_error()` stays reachable.

## What happened

macOS takes the buffers of every socket on the machine from one shared pool (mbufs). When the pool is empty, a send or a connect fails at once with `ENOBUFS`, even though the socket itself has room. Linux makes the sender wait instead, so the same program sees no error there.

giong makes macOS behave like Linux for a while: a stream write or connect that gets `ENOBUFS` is tried again after 1 ms, then 2, 4, 8, 16 and every 32 ms (each step varied by up to a quarter), and fails with this code only when the pool has stayed empty for 2 seconds. The worker runs its other tasks in the meantime. A `time::timeout` shorter than that ends the wait first, with its own error, and dropping the future cancels it with nothing sent. A connect whose handshake the shortage broke is tried again on a new socket within the same 2 seconds. A datagram send fails with this code at once, since a datagram may be dropped.

The pool usually runs dry because sockets hold data that nobody reads: each one keeps up to its receive buffer (`SO_RCVBUF`) in the pool.

## How to fix it

- Read from every connection promptly, and close the ones you no longer read from.
- Cap the number of connections that can hold unread data at once (a semaphore around the work, or a lower connection limit on the server).
- Lower `SO_RCVBUF` and `SO_SNDBUF` if the program raised them.
- `netstat -m` shows how much of the pool is in use and how many requests for it were denied.
